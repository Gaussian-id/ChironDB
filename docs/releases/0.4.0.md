# ChironDB 0.4.0

Changes on top of 0.1.0-beta.3. They come from the 19 November 2026 red-team
campaign against the beta.3 build. This is the first version on the plain
`x.y.z` line; there is no `0.1.0-beta.4`. No `v0.4.0` tag or image is
published yet.

## Breaking changes

### Installation-wide admin operations need installation authority (RT-11)

Applies only when tenant enforcement is `enforced`. With `disabled` (the
single-tenant default) and `dry-run` nothing is refused; `dry-run` logs each
request that `enforced` would refuse.

Before this change, any key with `role: "admin"` could run installation-wide
operations even when it was bound to one tenant. A tenant-B admin could delete
or snapshot collections holding tenant A's rows, and a snapshot is the whole
installation.

Now these operations need the `admin` role **and** installation authority:

- snapshot and restore (including the `/stream` variants), shard move;
- delete collection, payload schema change, compaction, `calibrate`,
  `cold/tier`, `wal_archive/prune`;
- `/metrics` and the `/ws/*` event and metric streams;
- the same operations over gRPC (`PERMISSION_DENIED`) and ChironWire.

Separately, gRPC server reflection now requires the `admin` role (RT-61).

A key has installation authority when it has no `tenant_id`, or when it is
granted the new `installation:admin` capability. An operation with no
collection (snapshot, restore, shard move, metrics, event streams) is also
refused to a key with `allowed_collections`, because it reaches every
collection. Creating a collection is unchanged and stays available to tenant
admins.

**Who must act:** multi-tenant installations running with
`--tenant-enforcement enforced` whose operator keys carry a `tenant_id` or an
`allowed_collections` list. Those keys now receive `403 Forbidden` on the
operations above, with this body:

```text
installation-wide operation requires the 'installation:admin' capability for tenant-bound admin keys; run `chironctl security installation-check --rbac-config-file <file>` or see docs/TENANT_ISOLATION.md#installation-wide-administration-needs-installation-authority
```

Keys below the `admin` role still get the plain `forbidden`.

**Recommended upgrade path**

1. **Scan the RBAC file** before upgrading. The check reads the file only, so
   it runs anywhere, including in CI:

   ```bash
   chironctl security installation-check --rbac-config-file ./rbac.json
   ```

   ```text
   b-admin tenant=tenant-b reason=missing_installation_capability: add "installation:admin" to this key's capabilities, or remove its tenant_id
   1 of 9 keys need a change before --tenant-enforcement enforced; see docs/TENANT_ISOLATION.md#installation-wide-administration-needs-installation-authority
   ```

   It lists every `admin` key that `enforced` will refuse, with the reason
   and the fix, and never prints key values. It exits `1` when any key needs
   a change and `0` when none do, so it can gate an upgrade step. `--json`
   prints the same report as `{keys_checked, ready_for_enforced, findings[],
   doc}`. Keys below the `admin` role are not listed: they were never allowed
   these operations.

2. **Decide per key.** Tenant admins that only manage their own tenant need
   no change; losing installation-wide power is the point of the fix. For each
   genuine operator key, either remove its `tenant_id`, or add the capability:

   ```json
   { "id": "ops", "key": "example-only-ops-key-replace-before-use", "tenant_id": "acme",
     "role": "admin", "capabilities": ["installation:admin"] }
   ```

   For a `collection_allowlist` finding, remove `allowed_collections` from
   that key, or run snapshot, restore, shard move and metrics with a separate
   operator key.

3. **Optional: rehearse with `dry-run` on a staging copy, not in
   production.** The server refuses to start in `dry-run` when any listener
   is on a non-loopback address or the installation is initialized
   (`chironctl security init`): it exits with "production listeners require
   --tenant-enforcement enforced after tenant migration". This is deliberate.
   `dry-run` also stops enforcing tenant isolation for data, so it must not
   face real clients. Do not use `CHIRONDB_ALLOW_INSECURE_NON_LOOPBACK` to get
   around it on a production host.

   To rehearse, start the new version on a staging host or a spare process
   with every listener on `127.0.0.1`, the updated RBAC file and
   `--tenant-enforcement dry-run`, then point your operator automation at it.
   Nothing is refused; every operation `enforced` would refuse logs one
   warning that names the key, its tenant, the operation, the reason and the
   fix:

   ```text
   WARN chirondb::rbac: tenant dry-run: installation-wide operation would be denied under enforcement principal=b-admin tenant="tenant-b" operation="POST /admin/snapshot" reason="missing_installation_capability" fix="add \"installation:admin\" to this key's capabilities, or remove its tenant_id" doc="docs/TENANT_ISOLATION.md#installation-wide-administration-needs-installation-authority"
   ```

   Over HTTP, `operation` is the method and route. Over gRPC it is
   `grpc <rpc>`, for example `grpc snapshot`, and over ChironWire it is
   `wire <operation>`, for example `wire compact`.

   The scan already covers every key in the RBAC file. The rehearsal adds
   which keys your automation actually uses for installation operations. If
   you cannot rehearse, rely on the scan.

4. **Upgrade with `enforced`.** When the scan exits `0` (and the rehearsal,
   if you ran one, logged no installation warnings you did not expect),
   restart production on the new version with the updated RBAC file and
   `--tenant-enforcement enforced`.

Snapshot contents are still not filtered per tenant. A snapshot is always the
whole installation, which is why it is gated instead. See
[Tenant isolation](../TENANT_ISOLATION.md#installation-wide-administration-needs-installation-authority).

## Security fixes

- **SQL nesting DoS (RT-40):** deeply nested SQL no longer overflows the stack
  and aborts the process. Expression trees are limited to 32 levels, including
  flat boolean chains such as a long `OR` list, and the limit is checked while
  parsing, so a refused statement never builds a deep tree. Set operations and
  array expressions, already outside relational v1, are refused before
  parsing. The PostgreSQL-wire vector parser has its own depth limit of 32. A
  rejected query gets HTTP 400 or a PostgreSQL `ErrorResponse`. A new
  `relational_sql` fuzz target covers the parser.
- **Nested function-call parse time (RT-40b):** the SQL parser dependency
  moves from sqlparser 0.62 to 0.64. On 0.62, parse time grew exponentially
  with nested function calls: `abs(abs(...))` 24 levels deep took about 12 s
  of CPU. The newer parser does not have this behaviour. Its grammar also
  accepts PostgreSQL `ORDER BY ... USING <operator>`, which relational v1
  rejects as unsupported.
- **Degenerate filters (RT-41, RT-42):** empty or inverted numeric ranges
  return an empty result instead of panicking; a reversed temporal interval and
  unknown or ill-typed filter operators return 400.
- **Tenant scoping and headers (RT-12, RT-13 partial, RT-50, RT-61):**
  `index_status` reports per-tenant counts to tenant-scoped readers; responses
  carry `X-Content-Type-Options: nosniff` and `Cross-Origin-Resource-Policy`,
  and HSTS on TLS listeners. A tenant key without `allowed_collections` still
  sees every collection name, but not the rows.
- **Log injection (RT-OBS-1):** control and bidirectional characters in
  client-supplied text are escaped before logging.

## New: opt-in write bounds for vectors (RT-20, RT-21)

Collections accept three optional limits, checked on every write:

| Field | Applies to | Effect |
| --- | --- | --- |
| `max_vector_norm` | dense and named vectors | rejects a vector whose L2 norm is above the limit |
| `max_sparse_nnz` | sparse vectors | rejects more than this many non-zero entries |
| `max_sparse_weight` | sparse vectors | rejects any absolute weight above the limit |

All three default to unset, which means unbounded and matches previous
behaviour (and Qdrant's). They are set when the collection is created, over
HTTP, gRPC, ChironWire or ChironQL `WITH`, and cannot be changed afterwards.
They are not enforced on writes a follower replays from its leader.

**Why you may want them:** with the `dot` metric, one vector with a huge norm
outranks every other point for almost every query. Without a bound, a writer
who can insert a single point can take over the top results. Set
`max_vector_norm` a comfortable margin above your embedding model's largest
legitimate norm.

When `max_vector_norm` is unset on a `dot` collection, the server logs a
rate-limited warning when it accepts a vector with an extremely large norm, so
operators notice the pattern without a configured bound. See
[Create a collection](../HTTP_API.md#create-a-collection).
